# Phase 4 Experiment Protocol — Deterministic Assessment and Digital Twin

## Status and scope

This protocol defines the Phase 4 evaluation of WealthGenie's deterministic
financial assessment and Financial Digital Twin. It was written before
implementation and is implemented by the code in `experiments/`.

**System under test:** the pure utilities in
`backend/src/utils/financialTwin.js`:

- `calculateTwin` — baseline and scenario metric calculation.
- `buildTwinPreview` — baseline/scenario preview and comparison.
- `compareTwinResults` — baseline-versus-scenario comparison.
- Input validation and threshold normalization.
- Recommendation rules and explanation payloads.
- Goal projection and month-end date clamping.

**Explicit non-goals:**

- Measuring real-world predictive accuracy.
- Claiming that recommendations improve financial outcomes.
- Claiming that explanations improve trust, comprehension, or financial
  literacy without a separate user study.
- Evaluating investment returns, taxes, inflation, or credit risk.
- Verifying the hosted Supabase deployment.
- Modifying or retraining the Global Findex experiment.

## Research questions

| ID | Question |
| --- | --- |
| RQ1 | Do the Digital Twin metrics match independent reference calculations across baseline and scenario results? |
| RQ2 | Do recommendation triggers fire exactly according to the documented rules? |
| RQ3 | Does baseline-versus-scenario comparison match the reference, and are goal months, dates, and boundaries correct? |
| RQ4 | Are deliberately invalid inputs rejected, valid inputs accepted, and repeated runs deterministic? |
| RQ5 | Do controlled one-input changes satisfy the documented directional invariants? |
| RQ6 | Do displayed metrics, goal fields, and recommendations include the required formula/rule, inputs, reason, assumptions, and heuristic distinction where applicable? |

## Synthetic dataset

The experiment uses a seeded synthetic dataset generated by
`experiments/lib/dataset.js`. It is **not** a real dataset, not a survey sample,
and not evidence about any population. It is kept separate from
`data/processed/findex_resilience.csv` and is never merged with Findex data.

### Generation parameters

| Parameter | Default | Meaning |
| --- | --- | --- |
| `seed` | `20261027` | Seed for the dependency-free `mulberry32` PRNG. |
| `profiles` | `200` | Number of seeded random profiles. |
| `includeEdgeCases` | `true` | Include the fixed deterministic boundary profiles. |
| `asOfDate` | `2026-10-27` | Fixed projection date, so results do not depend on the wall clock. |
| `thresholds.lowMandatoryCoverageMonths` | `3` | Heuristic low-coverage threshold. |
| `thresholds.highEmiBurdenPct` | `40` | Heuristic high-EMI threshold. |

### Random archetypes

The generator cycles through 14 archetypes:

`positive_surplus`, `zero_surplus`, `negative_surplus`, `emi_separate`,
`emi_included`, `low_emergency_savings`, `high_emergency_savings`,
`shock_funded`, `shock_unfunded`, `goal_achieved`, `goal_achievable`,
`goal_unreachable`, `zero_income`, `zero_expenses`.

Amounts are rounded to readable INR steps (100, 500, or 1000) after drawing from
documented ranges. The exact distributions and schema are in
`experiments/config/dataset-schema.json` and are stored with every run in
`dataset.json` and `run.json`.

### Deterministic edge cases

Twenty-six fixed profiles guarantee boundary coverage at any sample size:

- Zero income, zero expenses, zero outflows, and all-zero inputs.
- Break-even and deficit budgets.
- Coverage exactly at the 3-month threshold and just below it.
- EMI exactly at 40% of income and just above it.
- Fully funded, exactly funded, and unfunded unexpected expenses.
- Goal achieved exactly and above target.
- Unreachable goal with zero contribution.
- Floating-point month rounding (`0.07 / 0.01`).
- Month-end clamping in leap February and a 30-day month.
- No goal target, exact timeline, missed timeline.
- EMI included versus separate.
- Zero savings, a tiny goal, and large monetary values.

### Scenario suite

Each profile is evaluated against:

- `income_up` — income increases by 10% (minimum INR 1,000).
- `expenses_up` — expenses increase by 10% (minimum INR 1,000).
- `emi_up` — EMI increases by INR 5,000.
- `savings_up` — accessible savings increase by 25% (minimum INR 5,000).
- `shock` — one-time unexpected expense of 1.5× savings + INR 10,000.
- `combined_stress` — income down 10%, expenses up 10%, plus a shock.
- `goal_contribution_up` — only when a target exists; contribution increases by
  10% (minimum INR 1,000).

All other fields inherit the baseline. The suite is finite and is not an
exhaustive search of interaction effects.

## Independent reference implementation

`experiments/lib/reference.js` re-implements the documented formulas from raw
inputs. It does not import the assessment or Digital Twin maths. It uses a
separate `ceilMonthsIndependent` and an explicit day table for month-end
clamping.

The reference is a second implementation by the same project, not an external
mathematical oracle. Agreement reduces the risk of transcription errors but
does not prove that the formulas are the only reasonable financial model.

## Metric definitions and denominators

Let `N` be the number of evaluated results (baseline + scenario), and `S` the
number of scenario cases.

### Core metric assertions

For every result, compare the engine against the reference for:

| Key | Definition |
| --- | --- |
| `monthlyIncome` | `I` supplied. |
| `monthlyExpenses` | `E` supplied. |
| `accessibleSavings` | `S` supplied. |
| `emiPayments` | `M` supplied. |
| `emiIncludedInExpenses` | Boolean flag supplied. |
| `unexpectedExpense` | `U` supplied. |
| `monthlyOutflows` | `O = E + (EMI already in expenses ? 0 : M)`. |
| `monthlySurplus` | `P = I - O`. |
| `savingsRatePct` | `P / I × 100`; `null` when `I = 0`. |
| `livingExpenseCoverageMonths` | `S / E`; `null` when `E = 0`. |
| `mandatoryOutflowCoverageMonths` | `S / O`; `null` when `O = 0`. |
| `emiBurdenPct` | `M / I × 100`; `null` when `I = 0`. |
| `postShockSavings` | `max(0, S - U)`. |
| `unfundedShock` | `max(0, U - S)`. |

**Denominator:** `14 × N` assertions. Numeric equality uses a relative tolerance
of `1e-9`. The `expenseCoverageMonths` compatibility alias is checked
separately and is not part of the 14 core metrics.

### Goal assertions

For every result, compare:

`targetAmount`, `currentGoalSavings`, `remainingAmount`,
`assumedMonthlyContribution`, `estimatedMonths`, `unreachable`,
`requestedTimelineMonths`, `requiredMonthlyContributionForTimeline`,
`onTrackForRequestedTimeline`, `goalAchieved`, `estimatedCompletionDate`.

Rules:

- `remainingAmount = max(0, T - C)`.
- `assumedMonthlyContribution = monthlySavingsCapacity` when provided, otherwise
  `max(0, P)`.
- `estimatedMonths = 0` when `remainingAmount = 0`; otherwise
  `ceil(remainingAmount / contribution)` when contribution is positive;
  otherwise `null` and `unreachable = true`.
- `requiredMonthlyContributionForTimeline = 0` when remaining is zero;
  otherwise `ceil(remainingAmount / timeline)`; `null` without a target or
  timeline.
- `onTrackForRequestedTimeline = estimatedMonths <= timeline` when both exist.
- `goalAchieved = C >= T`.
- `estimatedCompletionDate = asOfDate + estimatedMonths` calendar months,
  clamped to the last valid day of the target month.

**Denominator:** `11 × N` assertions. A separate context check verifies that the
fixed as-of date is used in both the result and the goal projection.

### Recommendation trigger agreement

Documented rules:

| ID | Rule |
| --- | --- |
| `deficit` | `P < 0`. |
| `break_even` | `P = 0`. |
| `low_mandatory_coverage` | `S / O` is not null and `< 3` months. |
| `high_emi_burden` | `M / I` is not null and `> 40%`. |
| `unfunded_shock` | `U > S`. |
| `unaffordable_goal_contribution` | contribution `> 0` and contribution `> P`. |
| `goal_achieved` | `C >= T`. |

**Exact-set denominator:** `N` results. **Per-decision denominator:**
`7 × N` decisions (one expected-present/actual-present comparison per ID).
**Severity denominator:** the number of displayed recommendations. Precision,
recall, and agreement are reported per ID. A set match does not prove that a
recommendation is financially optimal.

### Comparison correctness

For each scenario:

- For each of 13 comparison metrics, compare `baseline`, `scenario`,
  `difference`, `percentageChange`, and `percentagePointDifference`.
  `difference = scenario - baseline`.
  `percentageChange = difference / |baseline| × 100` when baseline is nonzero
  and both values are finite; otherwise `null`.
- For each goal comparison field, compare the corresponding values, including
  `completionDate.direction` (`earlier`, `later`, `same`, or `null`),
  `goalAchieved.changed`, and `onTrackForRequestedTimeline.changed`.
- Compare the recommendation diff sets: `added`, `resolved`, `unchanged`, and
  `severityChanged`.
- Verify that `buildTwinPreview.baseline` equals a separately calculated
  baseline.

**Denominator:** `S × 105` assertions:
`13 × 5` metric checks + `35` goal-comparison checks + `4` recommendation-diff
checks + `1` baseline-consistency check. The overall comparison rate includes
all four families.

### Validation rejection and acceptance

Thirty-one deliberately invalid cases cover negative values, NaN, infinities,
non-numeric strings, booleans, blanks, missing required fields, unsupported
goals, zero targets, fractional or zero timelines, invalid dates, invalid
thresholds, and invalid preview objects.

Five valid cases cover a minimal profile, all-zero values, explicit nulls, a
leap day, and fractional amounts.

**Invalid denominator:** 31. A case passes only when it is rejected, the error
message matches the expected rule, and the message is non-empty and does not
contain `undefined` or `[object Object]`.

**Valid denominator:** 5. A case passes when it is accepted.

### Determinism

Every baseline is calculated twice, and every scenario preview is built twice.
The two results are compared by stable serialization.

**Denominator:** `N` repeated cases (`baseline profiles + scenario cases`).
This measures same-process, same-environment determinism only.

### Directional invariants

Seven controlled checks are evaluated per profile:

1. Increasing income must not reduce monthly surplus.
2. Increasing expenses must not increase monthly surplus.
3. Increasing accessible savings must not reduce living-expense coverage.
4. Increasing the unexpected expense must not increase post-shock savings.
5. Increasing a positive goal contribution must not increase projected months.
6. Increasing EMI when it is already inside expenses must not change surplus.
7. Increasing separately paid EMI must not increase surplus.

**Denominator:** applicable checks only. N/A cases are reported separately:

- Coverage is N/A when `E = 0`.
- Contribution is N/A when no target exists.
- Included-EMI is N/A when EMI is separate.
- Separate-EMI is N/A when EMI is included.
- An unreachable goal (`estimatedMonths = null`) is treated as infinite months.

These are mathematical properties of the implemented model under one-at-a-time
changes with fixed thresholds and as-of date. They are not evidence of
real-world financial improvement.

### Explainability coverage

Each displayed result is checked for:

- Result-level: `resultType = estimate`, disclaimer, assumptions, heuristic
  threshold label, explanations object, recommendations array.
- Metric-level: for 15 metric keys (14 core + alias), presence, formula, inputs,
  reason, and assumptions array.
- Goal-level: presence, formula containing `remaining = max(0, T - C)`, inputs,
  reason, assumptions.
- Goal-metric-level: for 11 goal fields, presence, formula, inputs, reason,
  assumptions.
- Recommendation-level: for each displayed recommendation, decision rule
  (`trigger`), formula, inputs, reason, assumptions, severity, heuristic flag;
  for heuristic recommendations, a threshold object with value, unit, and note.
- Formula-accuracy checks: eight metric formulas contain the documented tokens;
  the goal formula contains the documented remaining-amount formula.
- Uniqueness and threshold-presence checks for displayed recommendations.

**Denominator:** applicable checks. Recommendation checks are counted only when
that recommendation is displayed. Empty assumption arrays are accepted as "no
additional assumption stated." Coverage measures presence and internal
consistency, not wording quality or user comprehension.

## Analysis plan

For every measure, report:

- Passed / total and rate.
- Per-metric, per-field, per-ID, or per-invariant breakdown.
- Numeric maximum and mean absolute error and null mismatches where applicable.
- Explicit denominators.
- All failed cases, with examples, rather than only aggregate rates.

A test pass rate measures implementation consistency. It does not measure
real-world financial effectiveness, predictive accuracy, or user benefit.

## Artifacts

Each run writes to a new timestamped directory under `experiments/results/` and
never overwrites a previous run:

`run.json`, `dataset.json`, `profiles.csv`, `scenario-cases.csv`,
`metric-results.csv`, `goal-results.csv`, `comparison-results.csv`,
`recommendation-results.csv`, `validation-results.csv`, `invariants.csv`,
`explainability-summary.csv`, `explainability-failures.csv`, `failures.csv`,
`report.md`, and `manifest.json`.

`manifest.json` contains SHA-256 checksums and byte sizes for every artifact.

## Reproduction

From the repository root:

```bash
npm install
npm test
npm run experiment
npm run experiment -- --seed 20261027 --profiles 200
npm run experiment:publish
npm run build:frontend
```

`npm run experiment:publish` is the portable publish command. It avoids
shell-specific `--` argument forwarding issues (for example, Windows PowerShell
can drop forwarded flags). The equivalent direct command is
`node experiments/run.js --publish-doc`.

Verify a run manifest:

```bash
npm run experiment:verify -- experiments/results/<run>
```

The default seed, profile count, as-of date, and thresholds are recorded in
`run.json`. Reproduce exactly by keeping them and the Node.js version unchanged.

## Threats to validity

1. **Reference-implementation bias.** The reference is a second implementation
   by the same project, not an external oracle.
2. **Synthetic-data validity.** The archetypes are hand-designed and are not a
   probability sample of any population.
3. **Finite scenario suite.** The suite changes one input at a time plus one
   combined-stress case; it does not explore all interactions.
4. **Model scope.** No investment returns, interest, inflation, taxes, future
   income changes, borrowing, or asset sales are modelled.
5. **No user study.** Explainability coverage is not evidence of improved trust,
   comprehension, or financial literacy.
6. **Floating-point tolerance.** A relative tolerance of `1e-9` would hide
   smaller errors.
7. **Single environment.** Determinism is measured in one Node.js process on one
   platform; cross-version and cross-platform reproducibility are not proven.
8. **Hosted Supabase not verified.** Phase 4 runs locally with pure calculation
   utilities and does not require hosted credentials.
9. **No predictive-accuracy claim.** No outcome dataset links these inputs to
   future financial resilience.

## Findex isolation

The Global Findex experiment in `ml/` and its dataset in
`data/processed/findex_resilience.csv` are unchanged. The Findex model is a
survey-response classifier with coarse features, not an individual
financial-health predictor, and it is not used by the application. No synthetic
profile is merged into Findex data, and no Findex model, feature set, or result
is modified by Phase 4.
